# Deployment — Closed Beta

**Sprint:** 31.0 Closed Beta RC · durable production path added in Sprint 13.1

## Durable production (Render Blueprint — Sprint 13.1)

The canonical durable deployment is defined in **`render.yaml`** (infrastructure as code):

| Component | Definition |
|-----------|------------|
| Web service `ados-web` | Docker (`Dockerfile.web`) — API + same-origin SPA via `scripts/run_production_web.py` |
| PostgreSQL `ados-postgres` | Render managed Postgres (source of truth, unchanged) |
| Redis `ados-redis` | Render Key Value (required by production config policy) |

**Topology:** one process serves `/` (production `src/web/dist` build, `ADOS_SERVE_WEB=true`),
`/api/*`, `/management/*`, `/liveness`, `/readiness`, `/health`, `/metrics` on a stable
`https://<service>.onrender.com` URL. Telegram polling is *not* part of this service
(`ADOS_TELEGRAM_REQUIRED=false` — explicit web profile); the bot remains a separate run target.

**Migrations:** `scripts/run_production_web.py` runs `alembic upgrade head` at startup and
**refuses to start production** if migrations fail (`ADOS_SKIP_MIGRATIONS=1` only for
out-of-band migration flows). Provider `postgresql://` URLs are normalized to
`postgresql+asyncpg://` automatically (ConfigurationCenter + `migrations/env.py`).

**Deploy trigger (CI/CD):** push to `develop` → `.github/workflows/production-gate.yml`
(migrations gate, Sprint 13/13.1 health tests, CRM Sprints 8–13 suites, security suite,
frontend production build) → Render `autoDeployTrigger: checksPass` deploys only when all
checks pass → Render switches traffic only after `/liveness` health check passes. A failed
gate, build, or health check never replaces the running healthy deployment. Concurrency is
protected by the workflow concurrency group and Render's per-service deploy serialization.

**External verification:** `.github/workflows/production-verify.yml` (scheduled + manual)
checks root/HTML/assets/SPA route/liveness/readiness/CRM read/auth gate and compares the
deployed `revision` (exposed in `/liveness`) to `develop` HEAD. Configure the repository
**variable** `PRODUCTION_URL` to enable it.

**Health/readiness URLs:** `GET /liveness` (process + identity + revision),
`GET /readiness` (dependency-validated, 200/503), `GET /health` (full diagnostics + alerts).

**Rollback:** Render dashboard → service → Deploys → *Rollback* to a previous healthy
deploy (image-based, no rebuild), or revert the commit on `develop` and let the gate redeploy.

**Secrets (NAMES only, never values):** `IAM_JWT_SECRET`, `JWT_SECRET`, `API_JWT_SECRET`,
`SECURITY_MASTER_KEY` are **generated by Render** at provision time (`generateValue`);
`DATABASE_URL` / `REDIS_URL` are injected from the managed services; `BOT_TOKEN` is optional
(`sync: false` — set in the Render dashboard only). No deployment secrets exist in the repo.

**One-time owner action (blueprint activation):** Render dashboard → *New +* → *Blueprint* →
connect `okeysiri11/telegram-ai-crm-bot` → apply (`render.yaml` is picked up automatically) →
after first deploy, set the GitHub repository variable `PRODUCTION_URL` to the service URL.

**Manual recovery:** if the service is unhealthy, check *Events/Logs* in Render; redeploy the
last healthy commit via *Manual Deploy* → *Deploy commit*; database restores follow Render's
managed Postgres recovery (or `scripts/restore_postgres.sh` against `DATABASE_URL`).

## Stack

| Layer | Compose / path |
|-------|----------------|
| App API | `bot` service · Dockerfile |
| Postgres / Redis | `docker-compose.prod.yml` |
| Edge | `nginx.conf` (SPA + `/api` proxy) |
| Metrics | Prometheus + Grafana |

## Required secrets (prod)

- `POSTGRES_PASSWORD`
- `GRAFANA_ADMIN_PASSWORD`
- `IAM_JWT_SECRET` / `SECURITY_MASTER_KEY`
- `GOOGLE_CLIENT_ID` (production Google Sign-In)
- `VITE_DEMO_AUTH=false` for web build

## Deploy sequence

```bash
# 1. Build web
cd src/web && npm ci && npm run build && cd ../..

# 2. Configure .env.production (no default Grafana/Postgres passwords)

# 3. Start
docker compose -f docker-compose.prod.yml up -d --build

# 4. Health
curl -fsS http://localhost/health
```

## Verified public host (tunnel mode — Sprint 13)

When no VPS/Docker host is available, `scripts/start_public_host.py` brings up the
same production surface behind one HTTPS quick tunnel and refuses to report a URL
until public checks pass (root, assets, SPA route, `/liveness`, `/readiness`,
CRM read, auth gate). It serves the **production** `src/web/dist` build same-origin
through `scripts/serve_web_gateway.py` (never the Vite dev server) and reuses a
running API instead of starting a second bot.

```bash
npx vite build            # in src/web — production SPA build
.venv/bin/python scripts/start_public_host.py
# verified URL written to data/public_host.url (ephemeral: dies with the process)
```

See `docs/SPRINT_13_PRODUCTION_HOST_RECOVERY_RESULT.md` for the recovery record.
